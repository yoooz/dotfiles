# Tech News Collector

`references/sources.md` に定義された情報源から、最近公開された技術情報を収集する。

このSkillの目的は、すべての記事を網羅することではない。

ユーザーの興味・関心に合致し、技術的に面白い情報や、
今後の技術トレンドを理解するうえで価値のある情報を優先して収集する。

## 実行手順

1. `references/interests.md` を読み、ユーザーの興味・関心を把握する。
2. `references/sources.md` を読み、収集対象の情報源を確認する。
3. 各情報源から最近公開された更新情報を調査する。
4. 可能な限り一次情報を利用する。
5. ユーザーの興味との関連度が高い情報を抽出する。
6. 技術的な新規性や今後の注目度も考慮して評価する。
7. 原則として重要度の高い5〜10件程度に絞る。
8. `templates/daily-digest.md` の形式に従ってMarkdownを生成する。
9. `~/yoooz_vault/tech_news/tech-news-YYYY-MM-DD.md` として保存する。
   - ファイル名には必ず `tech-news-` 接頭辞を付ける。
   - デイリーノート（YYYY-MM-DD.md）とファイル名が衝突し、
     Obsidian の `[[YYYY-MM-DD]]` リンクが曖昧になるのを防ぐため。

## 情報の評価基準

以下の観点で各情報を評価する。

- ユーザーの興味・関心との一致度
- 技術的な新規性
- 従来の技術や開発方法との違い
- 今後広がりそうな技術や考え方か
- 開発体験を大きく変える可能性があるか
- 新しい設計パターンやアーキテクチャとして参考になるか
- 深掘りして学ぶ価値があるか
- 他の技術領域にも応用できそうか
- 技術コミュニティ全体に与える影響が大きいか
- Breaking ChangeやDeprecatedなど技術動向として重要か
- セキュリティやパフォーマンスに関する重要な知見があるか

## 優先度

### 高

以下に該当するものは優先的に取り上げる。

- 強く興味を持っている技術領域の大きなアップデート
- 新しいAI Agent / AI Codingの仕組み
- 新しいDeveloper Tool
- 新しい開発方法や設計思想
- 技術的に新規性の高い機能
- 大きなBreaking Change
- Deprecated / 廃止予定
- セキュリティ上重要な変更
- 今後のトレンドになりそうな技術

### 中

以下は内容に応じて取り上げる。

- 新機能
- SDK更新
- パフォーマンス改善
- Developer Experience改善
- 新しいAPI
- 新しい設計パターン
- 興味深いEngineering Blog
- 技術的に有用な事例紹介

### 低

原則として除外する。

- 軽微なUI変更
- マーケティング中心の記事
- 採用情報
- イベント告知のみの記事
- 技術的な内容がほとんどない企業ニュース
- 過去情報の再掲
- 内容が重複している記事
- 興味との関連が薄く、技術的新規性も低い情報

## 情報源に関するルール

可能な限り一次情報を利用する。

情報源の優先順位は以下。

1. 公式Changelog / Release Notes
2. 公式ドキュメント
3. 公式Engineering Blog / Technical Blog
4. 公式GitHub Release
5. 公式GitHub Issue / Discussion
6. 信頼できる二次情報

Hacker News、Reddit、X、個人ブログなどの二次情報は、
重要な情報を発見するための入口として利用してよい。

ただし、重要な技術変更については可能な限り公式情報で裏取りする。

## 調査時のルール

記事タイトルだけで判断しない。

重要そうな記事については本文を確認し、可能な範囲で以下を把握する。

- 何が発表・変更されたのか
- 従来と何が違うのか
- いつ公開されたのか
- いつから利用可能なのか
- Breaking Changeかどうか
- Deprecated / 廃止予定があるか
- 技術的にどこが新しいのか
- 今後どのような広がりがありそうか

不明な点がある場合は推測で断定しない。

公式情報から確認できない内容については、その旨を明示する。

## 関連度

各ニュースに、ユーザーの興味との関連度を5段階で付ける。

### ★★★★★

特に強く関心を持っているテーマに直接関係する。

例:

- AI Coding Agentの新しい仕組み
- Claude Code / Codex / Gemini CLIの大きな更新
- Agent Skills
- MCP
- Agent orchestration
- Supabaseの大きなアップデート
- Goの興味深い言語・ランタイム・ツール改善
- Flutter / Androidの新しい開発手法

### ★★★★☆

関心領域にかなり近く、読んでおく価値が高い。

### ★★★☆☆

主な関心領域ではないが、技術的に面白い、または学びがある。

### ★★☆☆☆

多少関係するが、優先して読む必要はない。

### ★☆☆☆☆

現在の興味とはほぼ関係がなく、技術的新規性も低い。

原則として★1〜2の情報はDaily Digestには含めない。

## 要約ルール

単なる記事要約にしない。

各ニュースについて、以下の3点を明確にする。

### 何が起きたか

発表内容や変更点を事実ベースで簡潔にまとめる。

### 何が面白いか

以下のような観点から技術的な面白さを説明する。

- 従来との違い
- 技術的な新規性
- 新しいアプローチ
- 面白い設計思想
- 開発体験への影響

### なぜ注目する価値があるか

`references/interests.md` を参照し、
ユーザーの興味との接点や、今後追いかける価値を説明する。

単に「便利そう」「重要そう」ではなく、
可能な限り具体的な理由を書く。

## 出力件数

原則として5〜10件とする。

重要なニュースが少ない日は、無理に件数を増やさない。

重要なニュースが多い場合でも、15件以上にはしない。

情報量よりも、
「読む価値のある情報だけが残っていること」
を優先する。

## カテゴリ

必要に応じて以下のカテゴリを利用する。

- AI / Agent
- Developer Tools
- Backend
- Infrastructure
- Database
- Mobile
- Web
- Authentication
- Security
- Cloud
- Programming Language
- Architecture
- Observability

必要であれば新しいカテゴリを追加してよい。

複数カテゴリに該当する場合は、最も重要なものを主カテゴリとする。

## 出力形式

`templates/daily-digest.md` を利用する。

各ニュースには最低限、以下を含める。

- タイトル
- カテゴリ
- 情報源
- 公開日
- 関連度
- 何が起きたか
- 何が面白いか
- なぜ注目する価値があるか
- 元記事URL

必要な場合のみ以下を追加する。

- Breaking Change
- Deprecated
- 移行期限
- リリース予定
- 後で検証したいこと

## 今日の注目

記事一覧とは別に、最後にその日の重要トピックを最大3件選ぶ。

単純に関連度だけで選ばず、以下を考慮する。

- 技術的な新規性
- 今後の広がり
- ユーザーの興味との一致
- 技術コミュニティへの影響
- 深掘りする価値

## 後で読む

興味深いがDaily Digest内では十分に深掘りできなかった情報は、
「後で読む」としてチェックリスト形式で残す。

## 最終確認

Markdownを保存する前に以下を確認する。

- 同じニュースが重複していないか
- 可能な限り公式情報へのリンクになっているか
- 古い情報を新着として扱っていないか
- 興味との関連が薄い情報が過剰に混ざっていないか
- 単なる要約で終わっていないか
- 「何が面白いか」が説明されているか
- 「なぜ注目する価値があるか」が説明されているか
- 推測を事実として書いていないか

品質を優先し、重要な情報がない場合は無理にニュースを生成しない。
