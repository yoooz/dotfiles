# Describe PR

初めてPRを読む人が「何をする変更か」「仕組みはどうなっているか」「いつ・どの条件で使えるか」を理解できる、自己完結した説明HTMLを作る。

## 説明の根拠を集める

- PRのURLまたは会話中の対象PRを使う。対象を特定できない場合だけ確認する。
- PR本文・差分・base/headのSHA・状態を取得し、必要な呼び出し元、型、スキーマ、設定、テストを読む。本文の説明だけを実装済みの事実として扱わない。
- 説明の基準はPRのheadとする。ローカルの未反映変更も説明するよう依頼された場合は、その範囲を明示する。調査用に現在の作業ツリーを上書きしない。
- 前提PRへの言及、追加API・DB変更・環境変数・feature flag・権限など、利用条件につながる変更を確認する。依存PRがあればリンクと現在の状態、何を提供するPRなのかを調べる。
- dev限定などの条件は、実際の判定箇所まで追う。ビルド時設定・実行時設定・URL・権限のどれによる条件かを区別する。devというホスト名だけで有効になるとは推測しない。
- 依存関係やデプロイ状況が不明なら、その点を未確認として残す。「依存PRの記載なし」と「依存なし」、「マージ済み」と「利用可能」を混同しない。

## 読者に伝える内容

PRの規模と内容に合わせて構成する。ファイル一覧の読み上げではなく、次の問いに答える。

### このPRは何をしているのか

- 冒頭で目的と主な変化を短く説明する。変更前後の具体例が役立つなら並べる。
- どんな機能で、誰が何を操作するとどうなるのか。画面や操作の図に、結果を添える。
- どんなデータを扱い、どこから取得し、どう変換・保存・表示するのか。主要なデータ構造と関係を図で示す。
- PRに合わせてER図、データフロー、状態遷移、リクエスト例、画面模式図などを選ぶ。DB変更がないPRに架空のテーブルを作らず、実際の型・状態・データの流れを説明する。
- 実データ、サンプル、ダミーデータ、説明用の図を明確に区別する。コード上の名称は、理解やソース確認に必要な部分だけ併記する。

### 条件はあるのか

- 前提となるPR、必要な環境・設定・権限・データ、操作やURLなどの開始条件を示す。
- devのみ／本番でも有効などの適用範囲と、条件を満たさない場合の挙動を説明する。判定するファイル・関数への根拠リンクを添える。
- 条件の組み合わせが理解の鍵なら、表や選択式のシミュレーターを使う。説明用のシミュレーターが実際のサービスを操作するように見せない。
- 必要に応じて制約、未対応範囲、検証済み事項と未確認事項を短く示す。テスト成功と実機・本番での確認は分ける。

## HTMLを作る

- 成果物はHTML。原則1ファイルにCSS・JavaScript・図・説明用データを収め、ブラウザで直接開けるようにする。本体のビルド・認証・DBに依存させず、説明のために実サービスを更新しない。
- 保存先はユーザー指定とリポジトリ規約を優先する。指定がなければ `/tmp/describe-pr/<owner>-<repo>-pr-<番号>.html` を使う。既存の別成果物を上書きしない。
- HTMLや付随成果物はコミット・ステージ・pushしない。追跡設定や `.gitignore` も変更しない。このスキルの実行をPR本文更新・レビュー投稿・マージ・公開の許可と解釈しない。
- 図はHTML/CSSやインラインSVGなどで埋め込む。インタラクションは条件や状態の理解に役立つ箇所に絞る。特定PRの配色やカード数を固定テンプレートにしない。
- PCとスマートフォンで読みやすくし、操作部品にはラベルとキーボード操作を用意する。色だけで状態や関係を伝えない。
- PRリンク、説明対象のhead SHA、確認日を記載する。ソースへのリンクは可能ならそのSHAに固定する。機密情報やトークンをHTMLへ埋め込まない。

## 確認して渡す

- 図・文言・条件分岐を調査した実装と照合する。PRの機能やデータ構造、条件が図から理解できるか確認する。
- 利用可能なブラウザでPC幅・狭い幅の表示と主要操作を確認する。シミュレーターがあれば条件の代表例と無効時も確認する。確認できなかった項目は明示する。
- 最後にHTMLへのクリック可能なリンクと、ブラウザのアドレス欄に貼れる `file:///...` の絶対パスを渡す。含めた内容と確認状況を短く伝え、未コミットであることを添える。
